# 研究報告: 圈圈叉叉遊戲

**Feature**: `001-tic-tac-toe` | **Date**: 2026-03-13

**語言要求**: 本文件 MUST 使用繁體中文。

## Phase 0 研究結論

### 決策 1：技術堆疊選擇

- **決策**: 採用純 HTML5 + CSS3 + 原生 JavaScript（ES6+），不引入任何 UI 框架（React、Vue、Angular 等）。
- **理由**: 圈圈叉叉遊戲為單頁靜態應用，狀態極簡（9 個格子 + 當前玩家 + 遊戲結果），不需要框架帶來的虛擬 DOM、元件系統或狀態管理機制。原生 JS 可直接操作 DOM，程式碼量少、可讀性高，符合「簡潔優先」憲章原則。
- **替代方案比較**:
  - React/Vue：增加建置工具設定（Vite/Webpack）與學習成本，對此規模的遊戲完全不必要。
  - TypeScript：增加轉譯步驟，對9格遊戲型別複雜度不足以證明引入必要性。

---

### 決策 2：測試策略

- **決策**: 使用 [Vitest](https://vitest.dev/) 做為單元測試執行器，測試遊戲邏輯（`game.js`），手動瀏覽器測試 UI 互動。
- **理由**: Vitest 支援原生 ES 模組、設定極輕量（單一 `vitest.config.js` 或零設定）、無需 Babel 轉譯，且可透過 `npm test` 一鍵執行。符合 TDD 要求（先寫測試、先看失敗、後實作）。遊戲邏輯（勝利判定、輪次切換、平局偵測）可完全與 DOM 分離，純粹以函式形式測試。
- **替代方案比較**:
  - Jest：需要額外 Babel/transform 設定以支援 ES 模組，比 Vitest 複雜。
  - 純手動測試：不符合憲章 TDD 原則。

---

### 決策 3：部署方式

- **決策**: 部署至 GitHub Pages，根目錄放置 `index.html`，直接啟用靜態頁面服務。
- **理由**: 需求明確為靜態前端，無後端需求。GitHub Pages 對靜態 HTML/CSS/JS 提供零設定部署（只需在 repo 設定中啟用 Pages，指向 `main` 分支根目錄）。
- **替代方案比較**:
  - Netlify/Vercel：功能過剩，增加外部服務依賴。
  - gh-pages 分支模型：此遊戲無建置步驟，根目錄即可直接服務，無需額外分支。

---

### 決策 4：遊戲狀態管理

- **決策**: 使用純 JavaScript 模組（`game.js`）以函式與閉包管理遊戲狀態，不引入 Redux、Zustand 或任何狀態管理庫。
- **理由**: 遊戲狀態僅包含：`board`（9 元素陣列）、`currentPlayer`（`'O'` | `'X'`）、`gameOver`（布林值）。這三個變數足以描述完整遊戲狀態，無需額外抽象。
- **替代方案比較**:
  - 類別（Class）封裝：可行但對此規模增加不必要的物件導向複雜度。
  - 全域變數：可行，但模組化函式更利於測試隔離。

---

### 決策 5：勝利判定演算法

- **決策**: 以靜態常數陣列定義八條勝利路徑，每次落子後逐一比對。
- **理由**: 圈圈叉叉棋盤固定為 3×3，勝利路徑永遠是固定 8 條（3 橫 + 3 縱 + 2 斜）。靜態陣列比動態計算更清晰、可讀且效能充足（每次落子最多比對 8 條 × 3 格 = 24 次比較）。
- **替代方案比較**:
  - 動態計算方向向量：對 3×3 棋盤過度設計，靜態陣列更直觀。
